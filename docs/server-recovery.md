# 한푼 서버 데이터 복구

## 두 단계의 저장

1. `hanpun_transactions`, `hanpun_monthly_plans`, `hanpun_age_profiles`의 쓰기와 같은 트랜잭션에서 `hanpun_private.ledger_mirror`에 최신 복제본을 저장합니다. 복제에 실패하면 원래 저장도 실패합니다. 복제본에는 원본 테이블/Auth를 참조하는 외래 키가 없으므로 원본 테이블 유실과 분리됩니다. 삭제된 기록은 tombstone으로 남기고 7일 이내 정리합니다.
2. `.github/workflows/backup.yml`이 6시간마다 실행되어 Supabase와 분리된 GitHub Actions 아티팩트에 암호화된 스냅샷을 저장합니다. 플랫폼 스케줄은 지연·실패할 수 있으므로 **마지막으로 성공한 백업 시점까지** 복구할 수 있습니다. 데이터 손실이 전혀 없는 실시간 다중 지역 저장을 의미하지 않습니다.

외부 백업은 AES-256-GCM으로 데이터를 암호화하고, 임시 데이터 키를 RSA-OAEP-256으로 감쌉니다. 공개 키만 저장소와 Edge Function에 있으며 개인 복구키는 저장소·정적 배포·Supabase에 없습니다. 복구키는 사이트 운영자가 별도 보관해야 합니다. Supabase 전체가 유실되어도 **외부 백업 파일과 개인 복구키가 모두 있으면** 복호화할 수 있습니다. 개인 키를 잃으면 복호화할 수 없습니다.

## 접근 제한

`hanpun-backup`은 GitHub Actions OIDC 토큰의 서명·발급자·audience·유효 기간을 검증하고, 저장소 ID `1431127078`, `main` 브랜치, 정확한 백업 워크플로 경로를 확인합니다. 브라우저 토큰·공개 앱 키·외부 저장소·PR 워크플로는 사용할 수 없습니다. GitHub에 Supabase 관리자 키나 장기 비밀 키를 복사하지 않습니다.

아티팩트에는 암호문만 있으며 서버 로그·Actions 로그에도 원문 가계부나 이메일을 출력하지 않습니다. 암호문은 공개 저장소의 아티팩트 접근 권한에 따라 내려받을 수 있으므로 개인 키 보관이 핵심입니다. 원본 데이터는 백업을 만드는 동안 Supabase 서버 메모리에서 처리합니다.

## 보관 및 정리

- GitHub 아티팩트: `retention-days: 7`.
- 서버 내부 삭제 복제본: 매시간 실행되는 `hanpun-retention-cleanup`에서 `6일 23시간` 이상 지난 항목을 제거해 정리 주기를 포함해 7일 이내 유지합니다.
- 삭제된 복제본도 삭제 표시와 함께 스냅샷에 포함됩니다. 내부 보관 최대 7일과 파일 생성 후 외부 보관 최대 7일이 이어지므로, 삭제된 정보의 외부 백업 최종 만료까지는 삭제 후 최대 14일이 걸릴 수 있습니다.
- AI 이용량: UTC 날짜 기준 현재와 이전 2일만 유지합니다.
- 백업 실행 메타데이터: 7일.
- 활성 가계부의 최신 복제본은 활성 원본과 함께 유지합니다. 기록을 삭제하면 삭제 표시가 적용됩니다.
- 로그인 전 기기 기록은 서버에 올라오지 않으므로 이 백업에 포함되지 않습니다.

## 외부 백업 확인

GitHub의 `Encrypted ledger backup` 실행 결과와 아티팩트를 확인합니다. 첫 업로드는 관련 파일을 `main`에 푸시할 때 실행되고, 이후 6시간 주기 및 `workflow_dispatch`로 실행할 수 있습니다. 업로드 후 서버의 `hanpun_private.backup_runs`에 아티팩트 ID·다이제스트·확인 시각을 기록합니다. 실패한 작업을 성공한 복구 지점으로 취급하지 않습니다.

## 읽기 전용 복호화 확인

성공한 작업에서 아티팩트를 내려받아 압축을 풀고 다음 명령을 실행합니다. 키와 복호화 결과를 웹사이트의 `public`·`dist`나 Git 저장소에 두지 마세요.

```sh
node scripts/restore-backup.mjs \
  --backup /secure/hanpun-ledger-backup.json \
  --key /secure/hanpun-backup-recovery-key.pem
```

이 명령은 계정 수·기록 수·백업 시각만 출력하고 DB에 쓰지 않습니다. 원문 기록은 터미널에 출력하지 않습니다. 암호문/메타데이터가 변경되거나 키가 다르면 복호화를 거부합니다.

## DB 복구

1. 대상 Supabase에 저장소의 DB 마이그레이션을 적용해 테이블·제약조건·서버 전용 복구 함수를 준비합니다. 다른 앱의 데이터나 인증 계정을 덮어쓰지 않습니다.
2. 인증 계정은 별도로 준비합니다. 기존 계정 UUID가 없다면 사용자가 Google로 다시 로그인한 후 이전 UUID→새 UUID 매핑 JSON을 준비합니다. 서버는 인증된 이메일 또는 동일한 소셜 계정 식별자가 일치하는 매핑만 허용합니다. 암호/인증 세션을 백업하거나 임의 계정을 생성하지 않습니다.
3. 대상 프로젝트의 서버 관리자 키를 권한 제한된 파일에 저장합니다. 다음 명령으로 DB에 대한 읽기 전용 검증을 실행합니다.

```sh
node scripts/restore-backup.mjs \
  --backup /secure/hanpun-ledger-backup.json \
  --key /secure/hanpun-backup-recovery-key.pem \
  --url https://PROJECT.supabase.co \
  --service-key-file /secure/service-key.txt \
  --user-map /secure/verified-owner-map.json
```

4. 대상·소유자 매핑·삭제 표시를 확인한 후에만 `--apply`를 추가합니다. 서버는 기본적으로 기존 행을 덮어쓰지 않고 없는 행만 복원합니다. 백업에 삭제 표시가 있는 행, 현재 복제본에 더 최근 삭제 표시가 있는 행은 복구하지 않습니다.
5. 사고로 발생한 대량 삭제를 되돌려야 한다면 운영자가 사고 시각과 승인된 복구 대상 ID를 검토한 후 그 대상의 삭제 표시를 처리해야 합니다. 일반적인 사용자 삭제를 자동으로 되살리지 않습니다. 원본 서버와 최신 삭제 표시까지 모두 잃은 경우 백업 시점 이후의 변경은 알 수 없으므로 운영자가 복구 대상을 확인해야 합니다.
6. 다른 프로젝트로 복구했다면 프런트엔드 설정·CSP 허용 주소·백업 스크립트의 대상 주소와 Edge Function 배포도 새 프로젝트에 맞게 변경합니다.

## 검증

SQL 트랜잭션 안에서 보험금/보험료·할부 행과 예산이 복제되는지, 복제본만 남은 테스트 행의 복원, 삭제된 행의 복원 차단, 사용자별 RLS를 확인한 뒤 전부 롤백합니다. 암호화 모듈은 서버 측 키 없이 복구되는지와 변조가 거부되는지를 테스트합니다. 실제 외부 아티팩트 업로드와 복호화 검증 결과는 `docs/verification.md`에 기록합니다.

스냅샷 스키마 3에는 AI 연령대 판정·동의 시각·유효기간도 포함됩니다. 사진이나 얼굴 특징값은 포함되지 않습니다. 복구 도구는 기존 스키마 2도 지원하며, 해당 백업에는 연령대 결과가 없으므로 복구 후 해당 기능은 재분석 전까지 제한됩니다.
